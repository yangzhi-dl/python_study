# AI 原生 Agent 工程补强实验（3.1–3.8）

> 本文是 [`langchain-langgraph-roadmap.md`](./langchain-langgraph-roadmap.md) 的补充实验路线。
>
> 原路线、模块 A–H 文档和现有练习题保持不变。本文只补原路线中尚未覆盖或覆盖不完整的工程能力，并把学习方式改成“AI 协作开发 + 故障诊断 + 证据验收”。

---

## 0. 最终目标与学习边界

最终不是背出 LangChain / LangGraph API，而是能够借助 AI 工具，独立完成下面四件事：

1. **能运行**：让 AI 生成的 Agent 最小版本可靠跑起来。
2. **能解释**：说清输入、状态、路由、工具、副作用和输出如何流动。
3. **能修坏**：面对检索失败、工具超时、上下文污染、越权调用等问题，能根据测试、日志和 trace 找到第一处异常。
4. **能迁移**：能换模型、换文档、增加工具或调整流程，而不是只能复现教程。

学习主线始终使用同一个项目：**不良品根因追溯 Agent**。

```text
用户输入批次号 / 产线 / 时间范围
  -> 检索工艺文件和历史案例
  -> 查询工单、质检、BOM 等工具
  -> LangGraph 编排状态与分支
  -> 输出根因候选、证据引用、置信说明和下一步建议
  -> 必要时等待人工确认
```

### 当前可以直接开始，不必等基础全部学完

仓库已经具备 Python A–F 的大部分练习。进入本文前不要求先把所有基础课程重新学一遍，只在遇到实际缺口时补对应知识：

| 实际缺口 | 什么时候补 | 最小补习目标 |
|---|---|---|
| Pydantic 三个核心方法 | 第一次做结构化输出时 | 会用 `model_validate()`、`model_dump()`、`model_json_schema()` |
| 装饰器 / `@tool` | 第一次定义工具时 | 看懂装饰前后函数发生了什么，不要求默写复杂装饰器 |
| 异步与流式 | 第一次接流式模型或 FastAPI 时 | 能解释 `await`、`async for`，能识别阻塞调用 |
| pytest | 第一次建立固定评测集时 | 会运行测试、看失败信息、写最小断言 |
| FastAPI | 服务化阶段 | 会改请求模型、异步路由、错误响应和健康检查 |

原则：**缺什么补什么，补到当前实验能继续即可。**

## 2. AI 原生快速学习法

### 2.1 采用的组织方式

三种方式中，本文采用组合方案：

| 方式 | 用法 |
|---|---|
| 单项目垂直切片 | 作为主线，同一个 Agent 从最小调用逐步加固到可部署版本 |
| 评测反推 | 每关先定义输入、预期和失败边界，再让 AI 生成最小实现 |
| 故障实验室 | 每关必须让 AI 注入至少一个受控故障，由学习者诊断和修复 |

不采用“读完全部理论 → 抄完整示例 → 换一道类似题”的传统顺序。

### 2.2 每关固定五步循环

1. **AI 搭骨架**
   - 你先写清输入、输出、禁止事项和验收条件。
   - AI 生成最小可运行代码和测试框架。
   - AI 不得擅自增加框架、数据库或抽象层。

2. **你来解释**
   - 不看 AI 总结，自己画出或口述：输入 → 状态变化 → 分支 → 输出。
   - 说出至少 3 个不变量和 2 个可能故障。
   - 解释不清的局部才回查官方文档或向 AI 追问。

3. **AI 制造故障**
   - 一次只注入一个故障。
   - AI 只给症状、失败输入和测试结果，不提前说答案。
   - 故障必须可以回滚，不接触真实敏感数据和生产系统。

4. **你来诊断**
   - 先写“假设 → 证据 → 区分性实验 → 最小修复”。
   - 不允许直接让 AI 重写整个模块。
   - 卡住时按“组件 → 关键 trace 字段 → 代码位置”逐级索取提示。

5. **自动验收**
   - 离线测试和固定评测集必须重跑。
   - 保存 baseline 与 candidate 的差异。
   - 最后做一个迁移题，例如换模型、换检索器或增加一个工具。

### 2.3 AI 和你的责任边界

| AI 可以负责 | 你必须亲自负责 |
|---|---|
| 查当前官方文档和兼容版本 | 判断需求是否真的需要 Agent |
| 生成最小骨架、测试夹具和假数据 | 定义输入输出、权限和副作用边界 |
| 解释陌生 API 的局部作用 | 解释完整数据流和状态变化 |
| 注入故障、给提示、审查 diff | 根据证据定位问题并选择最小修复 |
| 运行回归、整理对比报告 | 决定是否通过闸门、是否回滚 |

### 2.4 通用 AI 诊断提示词

```text
目标验收：
当前环境和依赖版本：
固定输入：
预期结果：
实际结果：
证据（命令、错误、日志、trace_id、指标）：
本次允许修改的范围：

请：
1. 区分已证实事实、推断和未知项；
2. 按证据列出最多 3 个原因；
3. 只设计 1 个最能区分这些原因的实验；
4. 实验确认后再给最小修改；
5. 给出回归验证和回滚方法；
6. 不修改无关模块，不用新增框架掩盖问题。
```

## 3. 贯穿项目与证据契约

### 3.1 最小业务数据

先使用假数据或脱敏样本，不等待真实系统接入：

- 10–20 条工单记录。
- 10–20 条质检记录。
- 3–5 份工艺或历史案例文档。
- 15–30 个固定问题，覆盖正常、无答案、歧义、越权和工具失败。

数据规模只需要足以暴露问题，不追求“大数据”。

### 3.2 每关必须保留的证据

```text
stage_id
代码与依赖版本
运行命令
固定输入
预期结果
实际结果
测试结果
trace_id（进入可观测阶段后）
Token / 延迟 / 成本（可获得时）
本次失败原因
最小修复
回滚方法
```

后续实现项目时可以使用下面的证据目录，但本文不创建这些目录：

```text
agent-hardening/
├── eval/             # 固定集与留出集
├── evidence/S0-S8/   # 命令、输出、trace、复盘
└── reports/          # baseline/candidate 对比
```

截图只能作为辅助证据，不能代替测试结果、结构化日志或指标。

## 4. S0：入口诊断与基线冻结

### 本关只补什么

确认当前 Python 能力足以开始框架学习，不要求先补完 A–H。

### 15 分钟首跑任务

运行一个包含 `.env` 配置、Pydantic 请求模型、异步假流和异常日志的最小程序。可以从现有模块 B、D、E、F 练习抽取代码，不新建复杂项目。

### 必交产物

- 10–20 条固定业务问题。
- 一份未优化的基线结果。
- 失败样本表：输入、预期、实际、失败类别。
- 当前 Python 缺口清单，只记录会阻塞下一关的项目。

### 故障注入

- 漏写一次 `await`。
- 给 Pydantic 模型传入错误字段类型。
- 移除一个必需环境变量。

### Go / No-Go

- **Go**：能独立运行、读懂 traceback，并至少修复一个故障。
- **No-Go**：连错误发生在哪一层都无法判断。只回补对应 Python 小节，然后重新验收。

## 5. S1：LLM 调用边界与输出控制

### 现有文档锚点

参考原路线的“2.2 LangChain 必须搞清的 6 个概念”与 Model、Message、OutputParser、流式调用部分，不重复抄写示例。

### 15 分钟首跑任务

让 AI 按当前官方文档生成一次最小模型调用，同时保留一个可替换 `base_url` 的 OpenAI-Compatible 配置。先完成同步文本返回，再加结构化输出。

### 必交产物

- 一个与具体 Provider 解耦的最小模型调用层。
- Pydantic 输出模型及 Schema 校验。
- 同步、异步或流式至少两种调用方式。
- 超时、有上限的重试、429 退避和失败返回契约。
- Token、延迟、模型名和估算成本记录。
- 一份 Temperature / Top-P 小实验：固定输入多次调用，记录差异；理解作用即可，不背公式。

### 故障注入

至少完成两个：

- 模型返回非法 JSON。
- 模拟 429 或临时网络错误。
- 模拟超时。
- 流式输出中途断开。
- 输入超过预设上下文预算。

### 验收证据

- Schema 校验失败不会伪装成成功结果。
- 重试有最大次数，只重试允许重试的错误。
- 超时可终止；流中断能返回明确状态。
- 相同 fake provider 输入可以离线稳定复现。
- 少量真实模型 smoke test 通过，不用真实调用代替离线测试。

### AI 追问

```text
请不要直接重写模型调用层。根据错误类型、尝试次数、耗时和原始响应，
判断问题属于 Provider、网络、Schema、上下文预算还是流消费；
只给一个区分性实验，确认后再给最小修改和回归测试。
```

## 6. S2：有依据、会拒答的 RAG

### 现有文档锚点

参考原路线“4.1 RAG”的加载、切块、Embedding、向量库、检索和拼接流程。本文从“最小链路能跑”继续补质量与安全。

### 15 分钟首跑任务

选 3–5 份脱敏文档，先用最简单的切块和向量检索跑出 baseline。不要一开始同时引入多个 Loader、向量库和重排模型。

### 必交产物

- 至少支持纯文本和一种 PDF、Word、网页或表格来源。
- 标准化元数据：文档 ID、来源、页码/段落、更新时间、权限标签。
- 固定长度与语义切块的一次对比；父子块只在确有跨段语义问题时加入。
- 向量检索 baseline。
- 当 baseline 失败时，再逐项实验关键词/向量混合检索、Query Rewrite、Rerank。
- 回答中的引用信息。
- 无证据拒答策略。
- 文档级权限隔离测试。
- 固定检索问题集与 Recall@K 等最小指标。

### 故障注入

至少完成两个：

- 丢失页码或来源元数据。
- 加入关键词相同但结论相反的干扰文档。
- 用同义改写导致纯关键词检索漏召回。
- 让用户访问无权限文档。
- 提出知识库中完全没有答案的问题。

### 验收证据

- 所有事实性结论可以追溯到来源片段。
- 没有可靠证据时明确拒答，不用模型常识补全企业事实。
- 无权限文档在检索阶段就被隔离，而不是生成后再遮盖。
- baseline 与增强方案使用同一问题集比较。
- 只有固定集证明有效，才保留 Rewrite、Rerank 等复杂组件。

### AI 追问

```text
请根据解析结果、chunk 元数据、召回列表、排序分数和最终引用，
判断第一处问题在解析、切块、召回、重排还是生成。
不要一次修改多个阶段，只设计一个能区分问题来源的实验。
```

## 7. S3：有边界、可恢复的 Agent

### 现有文档锚点

参考原路线的 `create_agent`、LangGraph 七个概念、ReAct、Tool Calling、Checkpointer 和 Human-in-the-loop。

### 15 分钟首跑任务

先用 `create_agent` 快速看到一次工具调用，再用 LangGraph 把同一条链路显式拆成状态、模型节点、工具节点和条件路由。第一版只放 3 个只读工具。

### 必交产物

- 一张节点图，标明哪些步骤是确定性代码，哪些需要模型判断。
- `query_workorder`、`query_quality`、`query_bom` 三个只读工具。
- 工具参数的 Pydantic 校验。
- 工具白名单与调用权限。
- 最大轮数、总执行时间和单工具超时。
- 写操作的幂等键设计；即使第一版没有真实写操作，也要用 fake 工具验证。
- 危险操作人工确认节点。
- 节点失败后的安全终止或恢复路径。
- Prompt 注入、工具输出注入和越权调用测试。

### 故障注入

至少完成三个：

- 工具参数类型错误。
- 工具超时或返回脏数据。
- 同一写操作被重复调用。
- 模型持续调工具导致循环。
- 文档或工具结果中藏有“忽略系统指令”。
- 未授权用户请求危险工具。

### 验收证据

- 工具参数错误在执行前被拒绝。
- 副作用操作不会因重试重复执行。
- 达到轮数、时间或成本预算后安全退出。
- 危险操作未经确认绝不执行。
- 中断后能从明确的 checkpoint 恢复或给出可解释失败。
- 能解释为什么某个节点需要 Agent，而不能直接用普通函数。

### AI 追问

```text
请沿 trace 找到第一个不变量被破坏的位置。
分别列出模型决策、路由、参数校验、权限、工具执行和状态写入的证据，
不要只根据最终异常猜测根因。
```

## 8. S4：上下文与记忆工程

### 本关只补什么

把“记住所有聊天”拆成三种不同的数据：

| 层 | 内容 | 典型生命周期 |
|---|---|---|
| `messages` | 当前会话中要给模型看的消息 | 受上下文窗口限制 |
| `working_state` | 当前追溯任务的批次、已查工具、待确认动作 | 一次任务或 checkpoint |
| `long_term_memory` | 跨会话仍有价值的稳定事实或用户偏好 | 持久化并按需检索 |

### 15 分钟首跑任务

构造一段超过预算的长对话，先观察失败，再实现最简单的滑动窗口。随后只在确有信息丢失时加入摘要或长期检索。

### 必交产物

- 三层数据契约与明确的写入、读取、淘汰规则。
- 每次模型调用前的上下文预算计算。
- 滑动窗口、摘要压缩或按需检索中的最小组合。
- 原始对话保留与回放路径，摘要不能覆盖原文。
- 用户和 `thread_id` 隔离。
- 事实冲突时的更新时间或来源优先规则。

### 故障注入

- 两个会话共用错误的 `thread_id`。
- 摘要漏掉重要安全约束。
- 旧记忆覆盖新事实。
- 上下文超过预算。

### 验收证据

- 重启后可以恢复当前任务。
- 不同用户之间没有上下文串线。
- 压缩前后 Token 数有记录。
- 固定关键信息在压缩后仍可回答。
- 对摘要存在疑问时可以回查原始消息。

## 9. S5：回归评测与失败样本闭环

### 本关为什么优先级最高

Agent 是概率系统。“这次跑通”不能证明系统变好。评测最晚在本关正式固化，但固定样本应从 S0 开始积累。

### 15 分钟首跑任务

把已经出现的 10–20 个输入整理成机器可读固定集，为每条写出可判定预期。先跑一次 baseline，不急着优化。

### 必交产物

- 回归集与独立留出集，禁止混用。
- 每条 case 的输入、期望、标签来源和人工确认状态。
- baseline/candidate 对比报告。
- 失败样本进入回归集的规则。
- 至少覆盖以下指标：
  - 任务完成情况。
  - 工具选择和参数正确性。
  - 越权或重复调用。
  - 引用与拒答。
  - Prompt 注入等安全 case。
  - 步数、Token、延迟和估算成本。
  - 与简单规则/普通函数方案的对比。

### 故障注入

- 故意改坏一段 Prompt 或工具描述。
- 让一个新 case 变好，同时让旧 case 回归。
- 把测试样本混入调优样本，检查是否能发现数据泄漏。

### 验收证据

- 评测门禁能抓住故意制造的退化。
- 关键权限和安全 case 不允许回归。
- “效果提升”必须有相同输入、环境和指标的前后报告。
- 不只看平均分，还能列出哪些 case 变好、哪些变差。
- 失败时能执行回滚并重跑旧版本。

---

## 10. S6：端到端可观测与故障定位

### 现有文档锚点

参考原路线“4.2 可观测性”和“4.3 审计日志”。本文补全跨组件关联、指标与诊断能力。

### 15 分钟首跑任务

为一次请求生成统一 `trace_id`，让模型调用、检索、工具、状态变化和最终响应都携带它。先使用结构化日志，不急着搭大型监控平台。

### 必交产物

- 统一结构化事件格式：时间、`trace_id`、用户/会话、组件、输入摘要、输出摘要、耗时、错误、版本。
- 敏感字段脱敏规则。
- 模型、检索、工具、状态和最终响应的关联链。
- 请求量、成功率、平均步数、Token、延迟、错误率和估算成本。
- 按任务或用户聚合的预算与限流告警。
- 能重放或可视化一次执行轨迹。
- “模型、检索、工具、Prompt、状态”五类故障归因表。

### 故障注入

- 检索返回错误片段。
- 工具返回空数据但未报错。
- Prompt 版本未生效。
- 模型超时。
- 日志脱敏遗漏。
- 某一节点没有传递 `trace_id`。

### 验收证据

- 只给一个 `trace_id`，可以还原完整链路。
- 能找到第一个异常组件，而不仅是最后报错的位置。
- 敏感测试字段不会出现在日志中。
- Token 或耗时超过预算时确实触发告警。
- 能回答：问题来自检索、工具、Prompt、状态还是模型？依据是什么？

## 11. S7：服务化、发布与回滚

### 现有文档锚点

参考原路线“4.5 部署”和模块 H 的 FastAPI 内容。本文不搭完整平台，只做一条可验证的服务切片。

### 15 分钟首跑任务

把当前 Agent 暴露成最小异步接口，提供一次非流式和一次流式调用。随后再加入鉴权和限流，不先搭复杂网关。

### 必交产物

- 一个最小 OpenAI-Compatible 或清晰等价的服务接口。
- 服务鉴权、模型路由、限流、超时和健康检查。
- 缓存键包含用户/权限/版本等必要维度，避免跨用户串数据。
- Provider 故障时的明确降级策略。
- Prompt、模型配置、工具 Schema、索引分别版本化。
- 最小灰度/A-B 验证和回滚流程，可以在本地或测试环境模拟。
- 延迟、吞吐、首 Token 延迟、错误率和成本预算。

### 故障注入

- 在异步接口内部使用阻塞调用。
- 缓存遗漏用户或权限维度。
- Provider 宕机。
- Prompt 与索引版本错配。
- 候选版本的错误率或延迟恶化。

### 验收证据

- API 和流式契约测试通过。
- 并发测试不会因一个同步阻塞让所有请求排队。
- 能说清一次请求使用了哪个模型、Prompt、工具 Schema 和索引版本。
- 候选版本异常时可以回滚并重放固定评测集。
- 发布判断基于预先定义的 SLO，而不是“演示看起来正常”。

## 12. S8：可选进阶闸门——微调、量化、自托管

> S8 默认关闭。做出有证据的 **No-Go** 决策，同样算完成本节。

### 12.1 什么时候才允许进入

必须同时满足：

- S0–S7 已有可重复 baseline、固定评测集和指标。
- Prompt、Schema、RAG、工具和工作流已经用对照实验排除。
- 同一类错误在多个独立 case 中稳定出现，不是偶发 API 故障。
- 错误属于企业术语理解、稳定分类/抽取、固定输出或窄任务行为。
- 训练数据授权清楚，已经清洗，并能划分训练、验证、测试集。
- 有明确的质量、成本、延迟、隐私或离线运行目标。
- 有失败后的回退方案。

### 12.2 什么时候不应该进入

任一项成立就先停止：

- 需求只是补充会变化的知识：优先 RAG。
- 需求是明确业务规则：优先确定性代码。
- 问题来自解析、切块、检索、权限、工具或状态机。
- 没有固定评测集，或者测试数据混入训练集。
- 数据太少、标签不一致、来源或授权不清。
- 云模型已经满足质量、延迟和成本目标。
- 只是因为微调、自托管看起来更高级。
- 没有人负责本地模型监控、升级、安全和容量规划。

### 12.3 最短学习顺序

1. 理解 SFT、数据清洗和数据切分。
2. 用 LoRA 做一个小规模 challenger。
3. 在独立留出集上对比“通用模型 + Prompt/RAG”基线。
4. 只有存在真实偏好数据和明确偏好目标时，再了解 DPO。
5. 确认必须自托管后，再比较 FP16、INT8、INT4 和 GPTQ/AWQ。
6. 简单本地验证可从 Ollama 一类工具开始；需要 GPU 服务吞吐时再评估 vLLM/TGI 等推理框架。
7. GPU 调优必须由 profiling 结果触发，不凭感觉调参数。

### 12.4 AI 原生实验

AI 生成最小 `data → train → eval → serve` 骨架；你必须解释：

- 数据如何切分，如何避免泄漏。
- 哪些参数可训练，为什么选择 LoRA。
- baseline 与 challenger 如何公平比较。
- 量化损失、显存收益、吞吐和延迟如何权衡。
- 失败时怎样回退到通用模型 + RAG。

让 AI 分别注入：错标、重复样本、测试集泄漏、量化质量骤降、显存不足或批处理延迟异常。你需要根据数据统计、训练日志和基准报告定位。

### 12.5 最小对比验收

在相同测试集、输出 Schema、采样参数和硬件记录下比较：

- A：Prompt/RAG baseline。
- B：LoRA challenger，仅处理已证明的稳定行为缺口。
- C：量化本地模型，仅在自托管理由成立时测试。

至少比较：

- 任务成功率、引用/拒答、Schema 通过率。
- 目标错误簇改善和其他能力回退。
- p50/p95 延迟、首 Token 延迟、吞吐和冷启动。
- 单次或每千次成本、显存/内存占用。
- 部署时间、运维复杂度和故障恢复。

阈值必须在实验前填写。没有达到阈值时保留原 baseline；“证明微调不值得”也是有效实验结果。

### S8 AI 追问

```text
请先将失败 case 逐例分类为：
知识缺失、检索失败、Prompt/Schema、工具/工作流、数据标签、模型能力。

每个判断必须引用证据。只有模型能力类达到预设闸门时，
才提出最小 LoRA 或本地模型实验；否则输出 No-Go，
并指出下一项成本更低、可以被固定评测验证的改进。
```

## 13. 总体验收清单

完成 S0–S7 后，应能提供以下证据：

- [ ] 能用自己的话解释一次请求经过模型、检索、工具、状态和响应的完整链路。
- [ ] 结构化输出失败、429、超时和流中断都有受控结果。
- [ ] RAG 回答带引用、无证据会拒答、无权限文档不会被召回。
- [ ] Agent 有参数校验、权限、幂等、轮数/时间预算和人工确认。
- [ ] 会话、任务状态和长期记忆分层，跨用户不串线。
- [ ] 固定集、留出集和失败样本可以重复运行。
- [ ] Prompt、工具或 RAG 变更后能生成 baseline/candidate 对比。
- [ ] 只凭一个 `trace_id` 能定位首个异常组件。
- [ ] 日志已脱敏，并能统计 Token、延迟、错误率和成本。
- [ ] 服务具备鉴权、限流、健康检查、降级、版本标识和回滚路径。
- [ ] 能用证据说明当前是否需要微调或自托管，而不是凭偏好选择。

真正的通关标准是：**能运行、能解释、能修坏、能迁移，并留下可复查证据。**

## 14. 当前停止清单

在固定评测证明有必要前，不做以下事情：

- 不同时学习多个 Agent 框架。
- 不从多 Agent 开始；优先单 Agent + 工具。
- 不同时接入多个向量数据库或多个文档解析框架。
- 不先搭 Kubernetes、服务网格、完整可观测平台或计费平台。
- 不为了“像生产”而提前引入消息队列、复杂微服务和分布式事务。
- 不把所有业务步骤都交给模型；确定性步骤继续用普通代码。
- 不因为一个 case 成功就宣布 Prompt、RAG 或 Agent 已优化。
- 不让 AI 一次性重写整个项目；坚持证据、区分性实验和最小修改。
- 不在没有数据、评测和业务收益时启动微调或采购 GPU。

## 15. 立即开始时，只做这三件事

1. 从 S0 选出 15 条固定问题，记录当前预期，不先优化。
2. 让 AI 生成 S1 的最小模型调用与 fake provider 测试骨架。
3. 故意制造一次非法结构化输出，亲自完成“证据 → 定位 → 最小修复 → 回归”。

完成后再进入 S2。不要提前把 S0–S7 全部代码一次性生成出来。
